# Migration Notes — `20260725120000_init`

**Companion to:** `prisma/migrations/20260725120000_init/migration.sql`
**Schema source:** `prisma/schema.prisma` (frozen, per Phase 1 review)
**Design reference:** `DATABASE_DESIGN.md`

This document explains every statement in the initial migration, states
which statements Prisma's migration engine would generate deterministically
from `schema.prisma` versus which were hand-written, and gives rollback
guidance. Read alongside the SQL file — section numbers below match the
`PART 1` / `PART 2` split and the numbered comment blocks inside it.

> **Note on how this file was produced:** this environment has no network
> access, so `prisma migrate dev`/`prisma migrate diff` could not be run
> against a live database to auto-generate `PART 1`. Instead, `PART 1` was
> hand-derived to be byte-for-byte consistent with what Prisma's migration
> engine deterministically produces from `schema.prisma` (type mapping,
> naming convention, and statement ordering all follow Prisma's documented,
> stable conventions). Before this migration is applied to a real database,
> run `prisma migrate diff --from-empty --to-schema-datamodel=prisma/schema.prisma --script`
> in an environment with the Prisma CLI and network access, and diff its
> output against `PART 1` of this file — they should match exactly. If they
> don't, trust the CLI output and treat any difference as a bug in this
> document, not in your schema.

## 2. PART 1 — Prisma-equivalent DDL

### 2.1 Enums (15)

Each maps one-to-one to a `enum` block in `schema.prisma`; the SQL type
name is the value from that enum's `@@map(...)`, not the Prisma-side PascalCase
name (e.g. Prisma's `Role` enum → SQL type `"role"`). Values are emitted in
declared order. No statement here needed hand-editing.

### 2.2 Tables (23)

One `CREATE TABLE` per model, columns in schema declaration order, using
each field's `@map` name. Every table gets a single-column UUID primary key
named `<table>_pkey`, matching every model's `id String @id @default(uuid())
@db.Uuid`.

**Important nuance on `id` columns:** `@default(uuid())` is a **Prisma
Client–side** default (the query engine generates the UUID before sending
the `INSERT`), not a PostgreSQL-level default — so these columns are
declared `UUID NOT NULL` with **no** `DEFAULT gen_random_uuid()` clause.
This is intentional and matches Prisma's actual generated SQL. **Consequence:**
any row inserted outside Prisma Client (a raw `psql` `INSERT`, a manual
seed script using raw SQL, a different service writing directly to
Postgres) must supply its own `id` value — the database will not generate
one. If you need DB-level UUID generation as a safety net independent of
the application layer, that would require adding `@default(dbgenerated("gen_random_uuid()"))`
to `schema.prisma` (a schema change, out of scope here per the freeze).

**`created_at` vs. `updated_at`:** `created_at` gets `DEFAULT CURRENT_TIMESTAMP`
(from `@default(now())`, which *is* a DB-level default). `updated_at` gets
**no** DB default — Prisma Client always supplies a value on both `create`
and `update` (that's what `@updatedAt` means), so the column only needs to
be `NOT NULL`. A raw SQL `INSERT` that omits `updated_at` will fail — by
design, so that no row can silently end up without a meaningful
last-modified timestamp.

**Type mapping used throughout**, per each field's Prisma type and any
`@db.*` attribute:

| Prisma | SQL |
|---|---|
| `String` | `TEXT` |
| `String @db.VarChar(n)` | `VARCHAR(n)` |
| `String @db.Char(n)` | `CHAR(n)` |
| `String @db.Uuid` | `UUID` |
| `Boolean` | `BOOLEAN` |
| `Int` | `INTEGER` |
| `DateTime` | `TIMESTAMP(3)` |
| `DateTime @db.Date` | `DATE` |
| `Decimal @db.Decimal(p,s)` | `DECIMAL(p,s)` |
| `Json` | `JSONB` |
| `String[]` | `TEXT[]` |
| enum | the mapped enum type name |

### 2.3 Indexes (72 `CREATE INDEX` statements: 24 unique + 48 non-unique)

Every `@@unique`/`@unique` and `@@index` in `schema.prisma` produces one
statement here, named `<table>_<col1>_[<col2>_...]_key` (unique) or `_idx`
(non-unique) — Prisma's standard naming convention. Cross-checked against
`schema.prisma`: **24 unique constraints, 48 non-unique indexes** — both
counts match the schema exactly (see §4, Verification).

Rationale for *which* indexes exist at all is covered in
`DATABASE_DESIGN.md` §4 — this file only confirms they were translated
correctly, not why each was chosen.

### 2.4 Foreign keys (41)

Every relation field with `@relation(fields: ..., references: ...)`
produces one `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` statement,
named `<table>_<column>_fkey`. `ON UPDATE CASCADE` is Prisma's default for
every relation (harmless here — UUID primary keys are never updated in
practice). `ON DELETE` matches each relation's explicit `onDelete` in
`schema.prisma`:

| Behavior | Count | Applies to |
|---|---|---|
| `RESTRICT` | 17 | Every relation where a parent must not be removable while financial/legal/public-trust records reference it — see `DATABASE_DESIGN.md` §6 for the full reasoning per relation. |
| `CASCADE` | 20 | Purely dependent child data (translations, rooms, availability, itineraries, staff, wishlist, notifications, coupon-usage-via-coupon/booking) that has no reason to survive an intentional hard delete of its parent. |
| `SET NULL` | 4 | `refunds.processed_by_id`, `reviews.booking_id`, `audit_logs.actor_id`, `homestay_staff.invited_by_id` — the child record must outlive the referenced row; only the attribution/link is lost. `homestay_staff.invited_by_id` uses `SetNull` for the same reason as `refunds.processed_by_id`: the inviter is a secondary participant in the record, not its owner, so their account must stay removable without being blocked by, or cascading into, staff rows they invited. |

**One deliberately unenforced reference exists outside this table:**
`Notification.relatedEntityId` has no foreign key at all in
`schema.prisma` (by design — the referenced entity type varies per
notification), so it produces no `ADD CONSTRAINT` statement here. This is
expected, not a gap.

## 3. PART 2 — Hand-written raw SQL, statement by statement

Each block below is wrapped in `DO $$ ... END $$` with an
`IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = '...')` guard
(constraints), or uses `CREATE INDEX IF NOT EXISTS` (indexes) — see §5 for
why, given Prisma's own migration-tracking already prevents double-application
in normal operation.

### 3.1 `bookings_target_matches_type_check`

```sql
CHECK (
  ("type" = 'HOMESTAY' AND "homestay_id" IS NOT NULL AND "tour_package_id" IS NULL)
  OR
  ("type" = 'TOUR_PACKAGE' AND "tour_package_id" IS NOT NULL AND "homestay_id" IS NULL)
)
```
**Why:** `Booking` is polymorphic over Homestay/TourPackage via two nullable
FKs (§5 of `DATABASE_DESIGN.md`) — this is the DB-level enforcement that
Prisma's schema language can't express. It's written *tighter* than a bare
"exactly one of two columns" check: it also ties the populated column to
the `type` discriminator, so a `HOMESTAY`-typed booking with
`tour_package_id` set (but `type` mismatched) is caught too, not just the
"both/neither null" case.
**Note:** this check does not constrain `room_id` — a `HOMESTAY` booking
with `room_id IS NULL` is currently allowed by this constraint. If room
selection should be mandatory at booking-creation time, that's an
application-layer rule today; tightening it at the DB level would be a
schema change (adding `room_id` to the check) and is out of scope for this
frozen-schema migration.

### 3.2 `reviews_target_matches_type_check`

Same pattern as 3.1, for `Review.targetType` / `homestay_id` /
`tour_package_id`. **Why:** identical polymorphic-association rationale.

### 3.3 `wishlist_items_target_matches_type_check`

Same pattern again, for `WishlistItem.targetType`. **Why:** identical
rationale; also backs the two `@@unique` constraints
(`user_id+homestay_id`, `user_id+tour_package_id`) which on their own would
silently allow a row with *both* columns null (nothing to prevent it) —
this check closes that gap.

### 3.4 `coupons_scope_at_most_one_check`

```sql
CHECK (NOT ("homestay_id" IS NOT NULL AND "tour_package_id" IS NOT NULL))
```
**Why this one is different:** `Coupon` has no `targetType` discriminator
and, unlike the three models above, **both columns being null is valid** —
that's an unscoped, platform-wide coupon (`appliesTo = ALL`). So this is
deliberately an "at most one," not "exactly one," constraint. Written this
way instead of copying the pattern from 3.1–3.3 to avoid a
false requirement that every coupon be scoped to something.

### 3.5 `payments_refunded_amount_bounds_check`

```sql
CHECK ("refunded_amount" >= 0 AND "refunded_amount" <= "amount")
```
**Why:** `Payment.refundedAmount` is a denormalized running total,
maintained by `refund.service.ts` (per `DATABASE_DESIGN.md` §12). This is
the second line of defense against a bug or race condition producing an
over-refund or negative balance — the primary defense is the application
transaction that increments this column alongside each `Refund` insert.

### 3.6 `reviews_rating_range_check`

```sql
CHECK ("rating" >= 1 AND "rating" <= 5)
```
**Why:** `rating` is stored as `SMALLINT` (range far wider than 1–5); this
was always documented as an app-layer-only validation in `schema.prisma`
(`/// rating Int @db.SmallInt // 1–5...`) — this closes that gap at the
database level, same reasoning as 3.5.

### 3.7 `blogs_tags_gin_idx`

```sql
CREATE INDEX IF NOT EXISTS "blogs_tags_gin_idx" ON "blogs" USING GIN ("tags");
```
**Why:** supports array-containment queries (`WHERE tags @> ARRAY['...']`)
for tag-based blog filtering. Standard GIN with Postgres's built-in array
operator class — no extension required. Flagged as a `TODO` directly in
`schema.prisma` since Prisma's `@@index` has no way to specify the `USING
GIN` index method.

### 3.8 Partial indexes (4)

Not individually requested but included under "additional indexes that
require raw SQL" — Prisma's `@@index` has no `WHERE` clause syntax, so a
partial index can only ever be added by hand:

| Index | `WHERE` | Why |
|---|---|---|
| `homestays_published_by_destination_idx` | `status = 'PUBLISHED' AND deleted_at IS NULL` | The public search/listing path filters to exactly this predicate on essentially every request; indexing only the live, published subset keeps the index a fraction of the size (and therefore faster) than the full-table composite index already covering the same columns. |
| `tour_packages_published_by_destination_idx` | same shape | Same reasoning, tour packages. |
| `notifications_unread_idx` | `is_read = false` | The unread-badge/list query is the hottest notification read path and only ever touches the (typically small) unread subset — much cheaper than scanning the full per-user history. |
| `bookings_active_upcoming_idx` | `status IN ('PENDING','AWAITING_PAYMENT','CONFIRMED') AND deleted_at IS NULL` | Ops/owner dashboards ("today's check-ins", "upcoming stays") only ever care about the active subset, not the full historical booking log. |

These are additive alongside the full-table composite indexes already
created in PART 1 — they don't replace `homestays_destination_id_status_deleted_at_idx`
etc., which are still needed for queries that filter on other status
values (e.g. an owner's dashboard showing `DRAFT`/`SUSPENDED` listings).

## 5. Idempotency & production-safety

**How idempotency is achieved, and why it differs between the two parts:**

- **PART 1** relies on Prisma's own migration-history mechanism: every
  applied migration is recorded (with a checksum) in the
  `_prisma_migrations` table, and `prisma migrate deploy` refuses to
  re-run a migration that's already recorded as applied. This is the
  standard, correct idempotency guarantee for Prisma projects — adding
  `IF NOT EXISTS` to `CREATE TABLE`/`CREATE TYPE` here would be unusual
  (not what Prisma actually generates) and would mask a real problem if
  this migration were ever mistakenly run twice outside Prisma's tracking
  (e.g. it would silently no-op against an already-different schema
  rather than erroring loudly).
- **PART 2** is hand-maintained SQL, which doesn't benefit from Prisma's
  own checksum tracking in the same way if it's ever edited or re-applied
  manually (e.g. via `psql` during a hotfix, or a `prisma db execute`
  outside the normal migrate flow) — so it's defensively guarded:
  `DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_constraint ...) ...`  for
  constraints, `CREATE INDEX IF NOT EXISTS` for indexes. Re-running PART 2
  against a database where it already succeeded is a safe no-op.

**Production-safety, specific to this being the *initial* migration:**

- Runs against an **empty** database — every `CREATE TABLE` and `ADD
  CONSTRAINT` (including all 6 `CHECK` constraints) validates instantly
  since there are zero existing rows to scan or violate. None of the
  "adding a constraint to a populated table" concerns (long table locks,
  `NOT VALID` + `VALIDATE CONSTRAINT` splitting, needing a maintenance
  window) apply here.
- The whole file is safe to run inside a single transaction (Prisma wraps
  `migrate deploy` in one automatically for PostgreSQL). Nothing in PART 2
  uses `CREATE INDEX CONCURRENTLY` (which cannot run inside a transaction)
  — deliberately, since on an empty/near-empty table a regular `CREATE
  INDEX` completes essentially instantly and doesn't justify giving up
  transactional atomicity.
- **This does not generalize to future migrations.** The moment any of
  these tables hold meaningful production data, adding a new index should
  use `CREATE INDEX CONCURRENTLY` (run outside a transaction, via a
  non-transactional Prisma migration or a manual `psql` step), and adding
  a new `CHECK` constraint to a populated table should use `ADD CONSTRAINT
  ... NOT VALID` followed by a separate `VALIDATE CONSTRAINT` to avoid
  holding a long-lived lock while scanning existing rows.
- **Take a database snapshot/backup immediately before running this in
  any real environment** — standard practice regardless of how safe a
  given migration looks on paper.

## 6. Rollback considerations

Prisma does not generate "down" migrations automatically — rolling back is
a deliberate, manual step. Two approaches, in order of preference:

**1. Restore from the pre-migration backup (strongly preferred).** Since
this is the initial migration on an empty database, this is nearly free —
there's no data to lose by restoring to "before this migration existed."

**2. Manual down script**, if a restore isn't available. Reverse order of
the file — drop what was added last, first:

## 7. Deployment checklist

1. Verify against a real Prisma CLI, as noted at the top of this document:
   `prisma migrate diff --from-empty --to-schema-datamodel=prisma/schema.prisma --script`
   should match `PART 1` of `migration.sql`.
2. Take a backup/snapshot of the target database (even though it's
   expected to be empty for a true "initial" migration).
3. `prisma migrate deploy` (not `migrate dev`) in every non-local
   environment — `deploy` never generates new migrations or prompts
   interactively, it only applies what's already committed.
4. Confirm `_prisma_migrations` shows `20260725120000_init` as applied
   before pointing the application at the database.
5. Smoke-test the 6 `CHECK` constraints and the polymorphic-association
   invariants they enforce with a throwaway insert/rollback in a
   transaction, before relying on them in application code.
