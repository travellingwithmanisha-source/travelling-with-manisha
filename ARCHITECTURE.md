# Travelling with Manisha — Architecture & Folder Structure

This document is the foundation blueprint. No feature code is built yet — this
defines *where* things will live and *why*, so the codebase stays scalable as
the team and feature set grow.

## Guiding principles

- **App Router + Route Groups** to separate marketing, auth, dashboard, and
  admin surfaces without polluting the URL structure.
- **Service layer** between API routes and Prisma so business logic isn't
  trapped inside route handlers (testable, reusable from server actions too).
- **Colocation of UI primitives vs. domain components** — shadcn's generated
  primitives stay untouched in `components/ui`, domain-specific composites
  live in feature folders.
- **Provider isolation** — every third-party SDK (Stripe, Razorpay,
  Cloudinary, Supabase, Google Maps) gets its own thin wrapper in `lib/` so
  swapping a provider later never means hunting through route handlers.
- **Type safety end-to-end** — Prisma-generated types flow into `types/`,
  Zod validators guard every API boundary and form.

## Why route groups (marketing) / (auth) / (dashboard) / (admin)

Each group gets its **own `layout.tsx`** — the marketing site doesn't carry
dashboard sidebar JS, the auth pages don't render the main nav, and the admin
area can enforce a role check at the layout level so every nested page is
protected automatically. None of these show up in the URL (parentheses are
stripped by Next.js), so routes stay clean: `/dashboard`, `/login`,
`/admin/trips`.

## Why a `services/` layer

API routes and server actions should stay thin — parse input, call a
service, return a response. The service layer owns transactions, authorization
checks, and cross-entity logic (e.g. `booking.service.ts` needs to touch
`trips`, `payments`, and `users` in one transaction). This also makes the
logic unit-testable without spinning up HTTP.

## Why `lib/<provider>.ts` wrappers

Stripe, Razorpay, Cloudinary, Google Maps, and Supabase each get a single
initialization point. Route handlers and services import the wrapper, never
the raw SDK — so credentials, retries, and config changes happen in one file.

## Why Prisma + Supabase together

Supabase is used purely for **Authentication** (and optionally storage/
realtime later); Prisma + PostgreSQL (the same Supabase Postgres instance)
is the ORM/query layer for the app's actual domain data (trips, bookings,
payments). `DATABASE_URL` points at the Supabase Postgres connection string,
so there's one database, two specialized clients.

## Payments: dual-gateway design

`services/payment.service.ts` exposes a provider-agnostic interface
(`createPaymentIntent`, `verifyPayment`, `handleWebhook`) with Stripe and
Razorpay as interchangeable strategies, selected by currency/locale (e.g.
INR → Razorpay, USD/international → Stripe). Webhooks are split into two
route handlers because each provider has a different signature-verification
scheme, but both resolve into the same `booking.service.ts` confirmation
call.
